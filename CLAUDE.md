# WindowsAppPacker

Репозиторий: `yosugie/WindowsAppPacker` (публичный).

## Кто пользователь / контекст

Пользователь обычно распространяет свои Python-инструменты как один
`.py` файл, который просто скачивают и запускают через `python
script.py` — если на компьютере уже стоит Python. Многим, кому он
отдаёт свои скрипты, Python ставить неудобно или не хочется.
WindowsAppPacker — это отдельная программа, которая берёт такой `.py`
скрипт и сама вызывает PyInstaller, чтобы получить один `.exe`, не
требующий Python на целевом компьютере.

## Зачем нужна программа

Раньше сборка `.exe` через PyInstaller делалась руками в консоли:
вспоминать флаги (`--onefile`, `--windowed`, `--icon`, `--add-data`,
`--version-file`...), собирать `--version-file` вручную для метаданных
EXE и т.д. WindowsAppPacker даёт для этого GUI: выбрал скрипт, иконку,
настройки — нажал одну кнопку — увидел лог сборки прямо в окне.

## Как это устроено технически

Один файл `WindowsAppPacker.py` (Python + CustomTkinter), как и другие
программы пользователя — так проще скачать и запустить без разбора
структуры папок. Внутри файла код разложен по смысловым блокам (в этом
порядке):

- `BuildConfig` — dataclass: все настройки одной сборки + `validate()`
- генерация Windows version-resource файла (`--version-file`) из
  версии/автора/описания — `build_version_file_content()` / `write_version_file()`
- `build_command()` — собирает CLI-аргументы PyInstaller;
  `BuildJob` — запускает сборку в отдельном потоке и стримит stdout
  построчно в GUI через очередь
- виджеты: `FilePathRow` (выбор файла + drag-and-drop), `LogConsole`
  (текстовое поле вывода лога, с тегами "success"/"error" для итоговых
  сообщений о сборке)
- `App` — главное окно (CustomTkinter): карточки "Основное" и
  "Метаданные" (у каждой своя кнопка "Очистить"), переключатель
  светлой/тёмной темы, кнопки сборки/отмены, прогресс-бар с процентом,
  сворачиваемая панель журнала

Пресетов, вкладки "Доп. файлы" и вкладки "Дополнительно" (произвольные
аргументы PyInstaller) в интерфейсе больше нет — пользователь убрал их
как ненужные. Компонент `DataFilesPanel` и модуль пресетов удалены
вместе с полями `data_files`/`extra_args` в `BuildConfig`.

Ранее проект был разбит на модули (`core/`, `ui/`), но пользователю
удобнее один файл, как и остальные его программы — при переносе логики
между модулями и файлом-версией код не менялся, только убраны
внутренние `import` между бывшими модулями.

Важные технические решения:

- Сборка запускается через `python -m PyInstaller ...` — PyInstaller
  должен быть установлен в том же окружении Python, что и сам
  WindowsAppPacker.
- Вывод PyInstaller читается построчно из `subprocess.Popen` в фоновом
  потоке и передаётся в GUI через `queue.Queue`, которую окно опрашивает
  через `after()` — так UI не подвисает во время сборки.
- Drag-and-drop файлов на поля выбора работает только если установлен
  необязательный пакет `tkinterdnd2` — если его нет, поле просто
  остаётся обычным (кнопка "Обзор..." работает всегда).
- Метаданные EXE (версия/автор/описание/имя продукта) вшиваются через
  сгенерированный `--version-file` — это ресурс формата Windows PE,
  PyInstaller на Linux/macOS его просто игнорирует с предупреждением
  (сама сборка при этом не ломается).
- Флаг "Запуск от имени администратора" — это штатный флаг PyInstaller
  `--uac-admin`, отдельный манифест руками не собирается.
- Тип сборки (Onefile/Onedir) в интерфейсе больше не выбирается — сборка
  всегда идёт как Onefile (`--onefile` жёстко зашит в `build_command()`),
  поле `onefile` в `BuildConfig` убрано как неиспользуемое.
- Светлая/тёмная тема переключается кнопкой в самом окне (переключатель
  "Тема:" сверху справа), а не системной настройкой Windows — обе палитры
  (словарь `THEMES`) используют один и тот же синий акцент. Переключение
  не пересоздаёт виджеты — каждый виджет регистрируется в `self._themed`
  при создании и перекрашивается через `_apply_theme()`. Специально НЕ
  вызывается `ctk.set_appearance_mode()` при переключении — эта функция
  рассылает обновление всем CTk-виджетам и вызывает полную перерисовку
  окна, что выглядит как перезапуск программы.
- Кнопка "Очистить" — своя у каждой карточки (`_clear_general()` для
  "Основное", `_clear_metadata()` для "Метаданные"), а не одна общая на
  всё окно — сбрасывает только поля своей карточки к значениям
  `BuildConfig()` по умолчанию, не трогая уже собранный EXE. Для очистки
  используется `_clear_entry()`, а не голый `entry.delete(0, "end")`: у
  `CTkEntry` плейсхолдер сам возвращается только если поле хоть раз
  теряло фокус (внутренний флаг `_is_focused` изначально `True`) — без
  явного вызова `_activate_placeholder()` поле, в которое пользователь
  ни разу не кликал, после очистки осталось бы пустым без подсказки.
- Переключение темы игнорирует повторный клик по уже активному варианту
  (`_on_theme_change` выходит рано, если тема не поменялась) — сегментная
  кнопка сама по себе вызывает callback даже при перевыборе того же
  значения, а полная перекраска ~30 виджетов вхолостую — лишняя работа.
- Прогресс-бар — `mode="determinate"`, процент считается по знакомым
  строкам в логе PyInstaller (`_BUILD_MILESTONES`: "Analyzing "/"Building
  PYZ"/"Building PKG"/"Building EXE"/"Build complete" → 10/35/55/80/100%).
  Это не реальный процент по байтам или шагам (PyInstaller такого не
  даёт), просто более честная имитация, чем indeterminate-анимация.
- Поле "Папка вывода" пустое по умолчанию (не `dist`) и подтягивается
  автоматически из папки исходного скрипта при его выборе — так же, как
  уже давно работает автоподстановка имени EXE. Если оставить пустым —
  PyInstaller сам создаст `./dist` рядом с собой.
- Поле "Версия" замаскировано под ввод только цифр и точек между ними
  (`validate="key"` + `_validate_version_input()` на регулярке
  `\d+(\.\d+)*\.?`) — буквы и спецсимволы физически не вводятся, точка
  подряд дважды тоже.
- Подсказки в полях выбора файла/папки не упоминают drag-and-drop
  ("Файл не выбран" и т.п.) — сам drag-and-drop как опциональная фича
  (через `tkinterdnd2`) в коде остался, но текст подсказки больше не
  обещает то, что чаще всего не работает "из коробки".
- Запятая в поле "Версия" автоматически заменяется на точку
  (`_on_version_keypress()`, привязан к `<KeyPress>` на внутреннем
  `tkinter.Entry` через `version_entry._entry` — у `CTkEntry` нет
  публичного `bind()`, который бы реально перехватывал нажатия клавиш,
  только у обёрнутого им сырого виджета) — актуально для русской
  раскладки и для numpad-точки, которая в русской локали Windows часто
  тоже вводит запятую.
- Панель журнала — сворачиваемая карточка (`_build_log_console()`):
  по умолчанию скрыта, разворачивается кнопкой-шевроном ("Журнал ⌄/⌃")
  или автоматически при старте сборки (`_set_log_expanded(True)` в
  `_start_build()`). Раскрытие/скрытие анимируется через `_animate_height()`
  — пошаговое изменение `self.geometry()` по `after()`, ease-out за ~14
  шагов, а не мгновенный скачок.
- Стартовый размер окна и `minsize()` не захардкожены, а вычисляются
  один раз в конце `__init__()` через `self.winfo_reqheight()` после
  сборки интерфейса (при свёрнутом журнале) — раньше `minsize(760, 600)`
  был угадан "на глаз" и оказался выше, чем реально нужно интерфейсу,
  из-за чего окно "залипало" при попытке сжать его по высоте раньше,
  чем реально требовалось. `_expanded_height` — это `_collapsed_height +
  LOG_PANEL_HEIGHT` (260px), используется как цель анимации при
  раскрытии журнала.

### Как запустить

```
pip install -r requirements.txt
pip install tkinterdnd2   # опционально, для drag-and-drop
python WindowsAppPacker.py
```

## Известные недочёты / ограничения

- Сборку `.exe` с иконкой/версией/UAC-манифестом нужно проверять именно
  на Windows — на Linux эти флаги либо игнорируются PyInstaller, либо
  ведут себя иначе. У ассистента нет Windows-среды, поэтому сборка
  проверялась через Xvfb на Linux (сам GUI и логика запуска процесса), а
  не итоговый `.exe` под Windows.
- Нет автоматических тестов — GUI и билдер проверялись вручную
  (headless-смоук через Xvfb, тестовая сборка одного скрипта). Если код
  поменяется, старая логика может незаметно сломаться без
  предупреждения.
- `tkinterdnd2` — необязательная зависимость. Если её нет, drag-and-drop
  тихо не работает, без единой ошибки — только обычный выбор файла через
  диалог.
- Прогресс-бар во время сборки показывает процент по нескольким
  знакомым строкам в логе PyInstaller (`_BUILD_MILESTONES`), а не
  реальный процент по шагам — PyInstaller такого не даёт. Если лог
  PyInstaller в будущей версии поменяет формулировки этих строк,
  прогресс перестанет двигаться (хотя сама сборка не сломается).
- Нет пресетов и произвольных аргументов PyInstaller — если это
  понадобится снова, придётся возвращать функциональность заново, а не
  просто раскомментировать: код был удалён, а не спрятан.
- Нет выбора Onefile/Onedir — сборка всегда Onefile. Если понадобится
  Onedir обратно, нужно возвращать и поле `onefile` в `BuildConfig`, и
  переключатель в интерфейсе.

## Правила коммитов git

Используем упрощённую версию Conventional Commits (не полную
спецификацию) — набор правил для соло-проекта без CI/CD и автоматического
версионирования.

**Главный принцип:** весь коммит целиком — тип, scope, заголовок, тело —
пишется на английском. Единственное исключение — слова/термины, взятые
прямо из программы (название кнопки, поля, столбца, детали и т.п. на
русском) — они вставляются как есть, но в кавычках `""`.

Правила:

1. Заголовок — на английском, формат `тип: краткое описание`, тип с
   маленькой буквы, в повелительном наклонении, простым понятным
   английским без сложных технических терминов.
2. Русские слова (названия кнопок, полей, элементов интерфейса, деталей
   и т.п.), встречающиеся в заголовке или теле — в кавычках, всё
   остальное вокруг них — на английском.
3. Тело — на английском, 1-2 коротких предложения, только ЧТО изменено,
   без "зачем/почему".
4. Никаких footer'ов и подписей: без Co-Authored-By, без ссылок на
   чат/сессию — коммит заканчивается сразу после тела.
5. Поле Author (техническое, в git) не трогаем — остаётся таким, каким
   его выставляет среда по умолчанию.
6. Один коммит = одно осмысленное законченное изменение. Не смешивать
   несколько разных правок в одном коммите.
7. Scope — используем. Короткое слово в скобках сразу после типа, на
   английском, с маленькой буквы: какой части проекта касается изменение
   (например `config`, `builder`, `presets`, `ui`, `metadata`). Если
   изменение общее и не относится к одной конкретной части — scope можно
   не указывать.
8. `!` и footer'ы (Refs/Closes и т.п.) пока не используем — в них нет
   смысла без issue-трекера и автоматизации. Если понадобится отметить
   breaking change — используем `!`, как в полной спецификации.

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
`build`, `ci`, `chore`, `revert` — всегда с маленькой буквы.

Примеры:

```
feat(ui): add "Отмена" button next to build action

Added a cancel button that terminates the running PyInstaller
subprocess and re-enables the "Собрать EXE" button.
```

```
fix(builder): quote paths with spaces in --add-data

Wrapped source and destination paths in the generated PyInstaller
command so folders with spaces in their names no longer break the build.
```

**Переход на полную спецификацию:** если проект вырастет, появится
команда или понадобится строгое соответствие стандарту — пользователь
скажет "переходим на полную спецификацию Conventional Commits". Тогда в
коммитах появятся `!`/BREAKING CHANGE и footer'ы (Refs/Closes) по
официальной спецификации (https://www.conventionalcommits.org/ru/v1.0.0-beta.2/),
вместо упрощённых правил выше.

## Как продолжать работу

Этот файл описывает план, смысл и задумку проекта, а также правила
коммитов — держать в актуальном состоянии по мере изменений. Перед
внесением изменений сначала разобраться в существующем коде
(`WindowsAppPacker.py`), а уже потом вносить изменения поверх него — не
переписывать заново и не додумывать логику по одному только этому
описанию.
