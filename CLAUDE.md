# WindowsAppPacker

Репозиторий: `yosugie/WindowsAppPacker` (публичный).

## Кто пользователь / контекст

Пользователь обычно распространяет свои Python-инструменты как один
`.py` файл, который просто скачивают и запускают через `python
script.py` — если на компьютере уже стоит Python. Многим, кому он
отдаёт свои скрипты, Python ставить неудобно или не хочется.
WindowsAppPacker — это отдельная программа, которая берёт такой `.py`
скрипт и сама вызывает PyInstaller, чтобы получить один `.exe`, не
требующий Python на целевом компьютере.

## Зачем нужна программа

Раньше сборка `.exe` через PyInstaller делалась руками в консоли:
вспоминать флаги (`--onefile`, `--windowed`, `--icon`, `--add-data`...).
WindowsAppPacker даёт для этого GUI: выбрал скрипт, иконку, настройки —
нажал одну кнопку — увидел лог сборки прямо в окне.

## Как это устроено технически

Один файл `WindowsAppPacker.py` (Python + CustomTkinter), как и другие
программы пользователя — так проще скачать и запустить без разбора
структуры папок. Внутри файла код разложен по смысловым блокам (в этом
порядке):

- `BuildConfig` — dataclass: все настройки одной сборки + `validate()`
- `build_command()` — собирает CLI-аргументы PyInstaller;
  `BuildJob` — запускает сборку в отдельном потоке и стримит stdout
  построчно в GUI через очередь
- виджеты: `FilePathRow` (выбор файла + drag-and-drop), `LogConsole`
  (текстовое поле вывода лога, с тегами "success"/"error" для итоговых
  сообщений о сборке)
- `App` — главное окно (CustomTkinter): карточки "Основное" и "Журнал"
  (у первой своя кнопка "Очистить"), переключатель светлой/тёмной темы,
  кнопки сборки/отмены, прогресс-бар с процентом

Пресетов, вкладки "Доп. файлы" и вкладки "Дополнительно" (произвольные
аргументы PyInstaller) в интерфейсе больше нет — пользователь убрал их
как ненужные. Компонент `DataFilesPanel` и модуль пресетов удалены
вместе с полями `data_files`/`extra_args` в `BuildConfig`.

Ранее проект был разбит на модули (`core/`, `ui/`), но пользователю
удобнее один файл, как и остальные его программы — при переносе логики
между модулями и файлом-версией код не менялся, только убраны
внутренние `import` между бывшими модулями.

Важные технические решения:

- Сборка запускается через `python -m PyInstaller ...` — PyInstaller
  должен быть установлен в том же окружении Python, что и сам
  WindowsAppPacker.
- Вывод PyInstaller читается построчно из `subprocess.Popen` в фоновом
  потоке и передаётся в GUI через `queue.Queue`, которую окно опрашивает
  через `after()` — так UI не подвисает во время сборки.
- Drag-and-drop файлов на поля выбора работает только если установлен
  необязательный пакет `tkinterdnd2` — если его нет, поле просто
  остаётся обычным (кнопка "Обзор..." работает всегда).
- Флаг "Запуск от имени администратора" — это штатный флаг PyInstaller
  `--uac-admin`, отдельный манифест руками не собирается.
- Тип сборки (Onefile/Onedir) в интерфейсе больше не выбирается — сборка
  всегда идёт как Onefile (`--onefile` жёстко зашит в `build_command()`),
  поле `onefile` в `BuildConfig` убрано как неиспользуемое.
- Светлая/тёмная тема переключается одной кнопкой в самом окне
  (`theme_toggle_btn`, показывает текущую тему — "Тёмная"/"Светлая" —
  и переключает по клику через `_toggle_theme()`), а не системной
  настройкой Windows — обе палитры (словарь `THEMES`) используют один и
  тот же синий акцент. Переключение не пересоздаёт виджеты — каждый
  виджет регистрируется в `self._themed` при создании и перекрашивается
  через `_apply_theme()`. Специально НЕ вызывается
  `ctk.set_appearance_mode()` при переключении — эта функция рассылает
  обновление всем CTk-виджетам и вызывает полную перерисовку окна, что
  выглядит как перезапуск программы. Раньше это был переключатель из
  двух кнопок (`CTkSegmentedButton`), пользователь попросил заменить на
  одну кнопку — сегментная кнопка и её тип в реестре тем удалены целиком.
- Кнопка "Очистить" карточки "Основное" (`_clear_general()`) сидит в той
  же строке, что и чекбоксы — не в отдельной строке под ними, чтобы не
  раздувать карточку лишней высотой. Сбрасывает поля карточки к
  значениям `BuildConfig()` по умолчанию, не трогая уже собранный EXE.
  Для очистки используется `_clear_entry()`, а не голый
  `entry.delete(0, "end")`: у `CTkEntry` плейсхолдер сам возвращается
  только если поле хоть раз теряло фокус (внутренний флаг `_is_focused`
  изначально `True`) — без явного вызова `_activate_placeholder()` поле,
  в которое пользователь ни разу не кликал, после очистки осталось бы
  пустым без подсказки.
- Прогресс-бар — `mode="determinate"`, процент считается по знакомым
  строкам в логе PyInstaller (`_BUILD_MILESTONES`: "Analyzing "/"Building
  PYZ"/"Building PKG"/"Building EXE"/"Build complete" → 10/35/55/80/100%).
  Это не реальный процент по байтам или шагам (PyInstaller такого не
  даёт), просто более честная имитация, чем indeterminate-анимация.
- Поле "Папка вывода" пустое по умолчанию (не `dist`) и подтягивается
  автоматически из папки исходного скрипта при его выборе — так же, как
  уже давно работает автоподстановка имени EXE. Если оставить пустым —
  PyInstaller сам создаст `./dist` рядом с собой.
- Подсказки в полях выбора файла/папки не упоминают drag-and-drop
  ("Файл не выбран" и т.п.) — сам drag-and-drop как опциональная фича
  (через `tkinterdnd2`) в коде остался, но текст подсказки больше не
  обещает то, что чаще всего не работает "из коробки".
- Заголовок окна (`self.title()`, то, что видно на панели задач Windows,
  не внутренний заголовок "WindowsAppPacker" в шапке карточек) — просто
  "WindowsAppPacker", без подписи.
- Значок окна (то, что видно на панели задач/в заголовке) — иконка
  "распаковка" (стрелка падает в открытую коробку), пришла от
  пользователя референсом; форма не менялась ни на пиксель — только
  перекрашен чёрный контур в фирменный синий (`THEMES["dark"]["accent"]`
  = `#0b63f6`) с сохранением исходного альфа-канала (сглаживания
  краёв). Встроен прямо в код и как base64 PNG (`_ICON_PNG_64`,
  `_ICON_PNG_32`, задаются через `self.iconphoto()`), и как base64
  `.ico` (`_ICON_ICO`) — без отдельного файла иконки рядом со
  скриптом, чтобы программа осталась одним файлом. Ссылки на оба
  `PhotoImage` держатся в `self._icon_images`: без этого Python собрал
  бы их мусором сразу после выхода из `__init__()`, и значок пропал бы.
- `.ico`-копия значка нужна отдельно от PNG из-за особенности
  CustomTkinter на Windows: и `CTk`, и `CTkToplevel` сами планируют
  `self.after(200, self._windows_set_titlebar_icon)`, который меняет
  иконку окна на дефолтный логотип CustomTkinter, если к этому моменту
  не был вызван `iconbitmap()`/`wm_iconbitmap()` (это отслеживается
  флагом `_iconbitmap_method_called`) — а `iconphoto()` этот флаг не
  трогает. Поэтому в общем хелпере `_apply_window_icon()` на Windows
  (`sys.platform.startswith("win")`) `_ICON_ICO` дополнительно
  распаковывается во временный файл (`tempfile.gettempdir()`, путь
  кешируется в `_icon_ico_path`, чтобы не писать файл заново на каждое
  окно) и передаётся в `window.iconbitmap()` — синхронно, до
  срабатывания таймера CustomTkinter, так что флаг успевает выставиться
  и иконка не перезатирается. На Linux/macOS этот блок не выполняется —
  там `iconphoto()` со своей задачей справляется сам.
  У каждого top-level окна своё собственное состояние иконки в Tk — оно
  не наследуется автоматически от главного окна, поэтому `_apply_window_
  icon()` вызывается отдельно и в `App.__init__()`, и в
  `MessageDialog.__init__()` (иначе у диалога ошибки в заголовке
  оставался дефолтный логотип CustomTkinter, а не наша иконка).
- Синий акцент (`THEMES["dark"]["accent"]` = `#0b63f6`, hover — `#3c82f8`)
  на всех кнопках — взято из CSS-примера кнопки, который принёс
  пользователь. CustomTkinter не поддерживает CSS `box-shadow` (двойное
  кольцо при наведении), поэтому эффект наведения сделан ближайшим
  доступным способом — сменой цвета заливки на `hover_color`, а не
  кольцом вокруг кнопки.
- Все кнопки создаются с `corner_radius=20` — специально больше, чем
  реально нужно: `CTkButton` сам ограничивает радиус до половины своей
  высоты (`min(corner_radius, height / 2)`), так что один и тот же
  параметр даёт каждой кнопке "таблеточную" форму независимо от её
  конкретной высоты (24/28/32/36px), без подбора числа под каждую.
- Ошибки проверки формы показываются через `MessageDialog` (свой
  `CTkToplevel`), а не `tkinter.messagebox` — нативный messagebox рисует
  ОС, а не Tk/CustomTkinter, поэтому он полностью игнорирует
  тёмную/светлую тему приложения (виден на скриншоте — всегда светлый).
  `MessageDialog` берёт текущую палитру `self.colors` на момент вызова
  (модальный, `grab_set()` + `wait_window()`, тема не может смениться,
  пока он открыт) и показывает только текст сообщения и кнопку OK в
  стиле остального приложения — без отдельной иконки/значка. Значок
  (цветной кружок с "✕"/"i" и параметр `kind`) был в первой версии, но
  убран: пользователь воспринял его как лишнюю некрасивую кнопку.
  `wraplength=360` (было 260) — окно специально пошире, чтобы не быть
  квадратным.
- Итоговые сообщения после сборки короткие: в статус-лейбле рядом с
  прогресс-баром — "Завершено!" / "Ошибка!", в самом журнале — "Сборка
  успешно завершена!" (зелёным) или "Сборка завершилась с ошибкой (код
  N)." (красным).
- Панель журнала сворачивается кнопкой-шевроном ("⌃"/"⌄") в шапке
  карточки "Журнал", на одном уровне с названием — не отдельной кнопкой
  "Очистить" внутри журнала (её убрали, чтобы не плодить кнопки: чистить
  журнал руками незачем, он и так очищается перед каждой новой сборкой).
  Заголовок и текстовое поле лога живут в одной и той же карточке
  (`_build_log_console()`), а не в двух визуально отдельных блоках.
  `_apply_log_layout()` только показывает/прячет виджет и настраивает
  веса строк; `_set_log_expanded()` поверх неё ещё меняет высоту окна —
  это разделение специально нужно для замера обеих высот в `__init__()`
  без побочных геометрических вызовов.
- Стартовый размер окна не захардкожен, а вычисляется через
  `self.winfo_reqheight()` дважды в конце `__init__()`: один раз с
  развёрнутым журналом (`_expanded_height` — стартовая геометрия,
  журнал по умолчанию открыт), один раз со свёрнутым (`_collapsed_height`
  — идёт в `minsize()`). Раньше единственный захардкоженный
  `minsize(760, 600)` был угадан "на глаз" и оказался выше, чем реально
  нужно интерфейсу, из-за чего окно "залипало" при попытке сжать его по
  высоте раньше, чем реально требовалось.
- Журнал по умолчанию открыт при запуске (`_log_expanded = True`,
  стартовая геометрия — `_expanded_height`). `_start_build()` всё равно
  вызывает `_set_log_expanded(True)`, если журнал был свёрнут руками
  (`if not self._log_expanded`) — на случай, если пользователь свернул
  его сам перед сборкой.

### Как запустить

```
pip install -r requirements.txt
pip install tkinterdnd2   # опционально, для drag-and-drop
python WindowsAppPacker.py
```

## Известные недочёты / ограничения

- Собранный `WindowsAppPacker.exe` умеет собирать другие EXE, но только
  если на компьютере отдельно установлен Python с PyInstaller — сам
  файл иконки/EXE не содержит внутри себя полноценный Python-рантайм,
  на котором можно было бы собрать произвольный чужой скрипт с любыми
  зависимостями (PyInstaller должен анализировать импорты именно этого
  скрипта, а значит нужна среда, где эти конкретные зависимости уже
  установлены — это ограничение самого PyInstaller, не WindowsAppPacker).
  Технически: `sys.executable` внутри запакованного EXE указывает на
  сам этот EXE, а не на python.exe, поэтому `build_command()` не может
  использовать его напрямую, как в незапакованном виде. Вместо этого
  `_find_system_python()` ищет настоящий Python через PATH (сначала
  `py -3` — лаунчер, который штатный установщик Python на Windows
  добавляет в PATH надёжнее, чем сам `python.exe`, — затем `python3`/
  `python`), проверяя каждого кандидата через `--version`. Раньше
  (до этого фикса) при попытке собрать что-то через уже собранный
  WindowsAppPacker.exe открывалось ещё одно окно самой программы
  (PyInstaller-бутлоадер просто перезапускал сам себя, игнорируя
  переданные флаги), а никакой реальной сборки не происходило.
  `BuildConfig.validate()`, стартовая проверка `_check_pyinstaller()` и
  сам `BuildJob._run()` — все три места на Windows (`getattr(sys,
  "frozen", False)`) сначала ищут Python, затем через
  `_python_has_pyinstaller()` (`python_cmd + ["-c", "import
  PyInstaller"]`) проверяют, что PyInstaller там установлен, и только
  тогда позволяют/выполняют сборку — либо показывают конкретную
  причину (Python не найден / PyInstaller не установлен для найденного
  Python, с готовой командой `pip install pyinstaller`) вместо молчаливой
  порчи или повторного окна.
- Сборку `.exe` с иконкой/версией/UAC-манифестом нужно проверять именно
  на Windows — на Linux эти флаги либо игнорируются PyInstaller, либо
  ведут себя иначе. У ассистента нет Windows-среды, поэтому сборка
  проверялась через Xvfb на Linux (сам GUI и логика запуска процесса), а
  не итоговый `.exe` под Windows.
- Нет автоматических тестов — GUI и билдер проверялись вручную
  (headless-смоук через Xvfb, тестовая сборка одного скрипта). Если код
  поменяется, старая логика может незаметно сломаться без
  предупреждения.
- `tkinterdnd2` — необязательная зависимость. Если её нет, drag-and-drop
  тихо не работает, без единой ошибки — только обычный выбор файла через
  диалог.
- Прогресс-бар во время сборки показывает процент по нескольким
  знакомым строкам в логе PyInstaller (`_BUILD_MILESTONES`), а не
  реальный процент по шагам — PyInstaller такого не даёт. Если лог
  PyInstaller в будущей версии поменяет формулировки этих строк,
  прогресс перестанет двигаться (хотя сама сборка не сломается).
- Нет пресетов и произвольных аргументов PyInstaller — если это
  понадобится снова, придётся возвращать функциональность заново, а не
  просто раскомментировать: код был удалён, а не спрятан.
- Нет выбора Onefile/Onedir — сборка всегда Onefile. Если понадобится
  Onedir обратно, нужно возвращать и поле `onefile` в `BuildConfig`, и
  переключатель в интерфейсе.
- Нет карточки "Метаданные" и вшивания версии/автора/описания/имени
  продукта в свойства EXE через `--version-file` — пользователь счёл её
  ненужной. Код (`BuildConfig` поля, генератор `--version-file`, маска
  ввода версии, зеркалирование "Имя продукта" из "Имя EXE") удалён
  целиком, а не спрятан — возвращать пришлось бы заново.

## Правила коммитов git

Используем упрощённую версию Conventional Commits (не полную
спецификацию) — набор правил для соло-проекта без CI/CD и автоматического
версионирования.

**Главный принцип:** весь коммит целиком — тип, scope, заголовок, тело —
пишется на английском. Единственное исключение — слова/термины, взятые
прямо из программы (название кнопки, поля, столбца, детали и т.п. на
русском) — они вставляются как есть, но в кавычках `""`.

Правила:

1. Заголовок — на английском, формат `тип: краткое описание`, тип с
   маленькой буквы, в повелительном наклонении, простым понятным
   английским без сложных технических терминов.
2. Русские слова (названия кнопок, полей, элементов интерфейса, деталей
   и т.п.), встречающиеся в заголовке или теле — в кавычках, всё
   остальное вокруг них — на английском.
3. Тело — на английском, 1-2 коротких предложения, только ЧТО изменено,
   без "зачем/почему".
4. Никаких footer'ов и подписей: без Co-Authored-By, без ссылок на
   чат/сессию — коммит заканчивается сразу после тела.
5. Поле Author (техническое, в git) не трогаем — остаётся таким, каким
   его выставляет среда по умолчанию.
6. Один коммит = одно осмысленное законченное изменение. Не смешивать
   несколько разных правок в одном коммите.
7. Scope — используем. Короткое слово в скобках сразу после типа, на
   английском, с маленькой буквы: какой части проекта касается изменение
   (например `config`, `builder`, `presets`, `ui`, `metadata`). Если
   изменение общее и не относится к одной конкретной части — scope можно
   не указывать.
8. `!` и footer'ы (Refs/Closes и т.п.) пока не используем — в них нет
   смысла без issue-трекера и автоматизации. Если понадобится отметить
   breaking change — используем `!`, как в полной спецификации.

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
`build`, `ci`, `chore`, `revert` — всегда с маленькой буквы.

Примеры:

```
feat(ui): add "Отмена" button next to build action

Added a cancel button that terminates the running PyInstaller
subprocess and re-enables the "Собрать EXE" button.
```

```
fix(builder): quote paths with spaces in --add-data

Wrapped source and destination paths in the generated PyInstaller
command so folders with spaces in their names no longer break the build.
```

**Переход на полную спецификацию:** если проект вырастет, появится
команда или понадобится строгое соответствие стандарту — пользователь
скажет "переходим на полную спецификацию Conventional Commits". Тогда в
коммитах появятся `!`/BREAKING CHANGE и footer'ы (Refs/Closes) по
официальной спецификации (https://www.conventionalcommits.org/ru/v1.0.0-beta.2/),
вместо упрощённых правил выше.

## Как продолжать работу

Этот файл описывает план, смысл и задумку проекта, а также правила
коммитов — держать в актуальном состоянии по мере изменений. Перед
внесением изменений сначала разобраться в существующем коде
(`WindowsAppPacker.py`), а уже потом вносить изменения поверх него — не
переписывать заново и не додумывать логику по одному только этому
описанию.
